# Banking ETL Pipeline

Учебный проект по построению ETL-пайплайна для обработки банковских данных с использованием Python и PostgreSQL.

## О проекте

Проект демонстрирует полный цикл обработки данных: загрузку исходных CSV-файлов, очистку и преобразование данных, загрузку в аналитические таблицы, формирование представлений и автоматические проверки качества.

Данные синтетические и предназначены для обучения.

## Архитектура


## Этапы обработки

1. Загрузка исходных CSV в схему `staging`.
2. Удаление полных дубликатов транзакций.
3. Преобразование строковых значений в типы `TIMESTAMP` и `NUMERIC`.
4. Загрузка очищенных данных в схему `clean`.
5. Создание аналитических представлений в схеме `analytics`.
6. Проверка количества строк, дубликатов, идентификаторов и проблем качества.
7. Запуск автоматических тестов.

## Аналитические представления

### `analytics.customer_summary`

Сводка по клиентам, включающая количество счетов, успешных транзакций и суммы операций в UZS и USD.

### `analytics.transaction_quality_issues`

Список транзакций с выявленными проблемами качества, например отсутствующей суммой, неизвестным счётом или датой, которую не удалось корректно разобрать.

## Запуск

### 1. Установите зависимости

```bash
python -m pip install -r requirements.txt
```

### 2. Создайте базу данных PostgreSQL

Создайте базу `banking_dwh` и настройте пользователя с необходимыми правами доступа.

### 3. Создайте staging-таблицы

Выполните SQL-файл `sql/01_staging.sql` в базе `banking_dwh`.

### 4. Подготовьте исходные файлы

Поместите `customers.csv`, `accounts.csv` и `transactions.csv` в `data/raw/`.

### 5. Запустите ETL

Из корня проекта выполните:

```bash
python src/run_pipeline.py
```

Скрипт запрашивает пароль PostgreSQL, если он не передан через поддерживаемую переменную окружения.

### 6. Запустите тесты

```bash
python -m unittest discover -s tests -v
```

Тесты PostgreSQL требуют доступную базу данных с уже загруженными результатами ETL.

## Контроль качества

Пайплайн выявляет отдельные проблемы качества данных, но не исправляет автоматически все бизнес-ошибки. Некорректная дата в учебном наборе сохраняется как `NULL` для последующего анализа. Транзакции с неизвестным счётом и отсутствующей суммой отражаются в отчёте качества.

Успешные проверки подтверждают выполнение реализованных правил, но не гарантируют полную корректность всех данных.

## Ограничения текущей версии

- Учебный набор данных небольшой и синтетический.
- Проверки ожидаемых количеств рассчитаны на текущий набор данных.
- Политика обработки некорректных дат пока содержит специальное правило для одной записи.
- Автоматизация Airflow и промышленное журналирование могут быть добавлены в следующих версиях.
